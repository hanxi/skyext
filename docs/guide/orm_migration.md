# ORM schema 迁移

ORM schema 描述的是「当前代码期望文档长什么样」，而数据库里还躺着按旧 schema 写下的文档。字段改名、结构拆分、补默认值这类变更没法靠 schema 自身完成：旧文档一进 `orm.new` 就会撞在类型检查上，加载直接失败。

迁移机制给每个集合维护一条**只能往末尾追加**的有序迁移链。文档里记一个 `_schema_version`，`dbmgr` 加载时把缺的那几步按序补上，并在把文档交给业务之前把结果写回数据库。

## 定义迁移

游戏层在 `game.orm.migrations` 模块（示例工程里是 `example/lualib/game/orm/migrations.lua`）里按集合分组声明：

```lua
return {
    role = {
        {
            version = 1,
            desc = "nick 改名为 name",
            migrate = function(doc)
                doc.name = doc.nick or ""
                doc.nick = nil
            end,
        },
        {
            version = 2,
            desc = "背包容量补默认值",
            migrate = function(doc)
                doc.bag_size = doc.bag_size or 30
            end,
        },
    },
}
```

| 字段 | 约束 |
| --- | --- |
| `version` | 整数，必须**等于它在数组里的下标**。迁移链是多人并行往末尾追加的，漏写或插队在 git 合并时不会产生冲突，却会让两份代码对「第 N 版长什么样」产生分歧；显式版本号把这种分歧提前成启动期报错 |
| `desc` | 非空字符串，出现在迁移失败的报错里 |
| `migrate` | `function(doc)`，**原地修改**传入的表，不需要返回值 |

`migrate` 拿到的是 MongoDB 解码出来的普通 Lua 表，还没有套上 ORM schema，所以才有能力把文档从旧形状搬到新形状。表里包含 `_version`（乐观锁计数）和业务字段，不包含 `_id`、`_fence`、`_schema_version`——这三个由 `dbmgr` 维护，迁移函数不该碰。

整个模块可以不存在：没有 `game.orm.migrations` 就等于所有集合都没有迁移链。但文件存在却加载失败（语法错误等）会让加载整体报错，而不是静默当成「没有迁移」。

## 加载时发生了什么

1. 读出文档的 `_schema_version`，缺失的老文档按 `0` 算，并把这个字段从文档里剔除（schema 里没有它）。
2. 对比该集合迁移链的长度（即当前代码的目标版本）：
   - 相等：什么都不做。
   - 文档版本更低：按序执行缺的那几步。
   - **文档版本更高**：拒绝加载。文档是更高版本的代码写下的，旧代码不认识新结构，继续跑只会把数据越写越坏——回滚部署时这条规则能保住存档。
3. 执行成功后立刻落库：整份 `$set` 回去，迁移删掉的字段 `$unset`，同时把 `_schema_version` 更新成目标版本、`_version` 加一。
4. 用迁移后的表构建 ORM 文档，交给业务。

**为什么要立刻落库**，而不是等下一次回存轮？迁移函数不保证幂等，进程若崩在中间，下次加载会从库里的旧版本号把同一条链再跑一遍；而且文档可能一直不脏，等下去就是永远不写。

**并发安全**：迁移写入沿用 `save_doc` 那套 `_version` 乐观锁，持有分布式锁时再叠上 `_fence` 条件。失配说明别的写者正在并发修改这一行，此时整个加载失败（返回 `schema migration write failed`），比带着半迁移的数据继续跑安全。迁移本身也在行锁内执行，同一进程不会重入。

新创建的文档天生就是最新结构，插入时就带上当前版本号（`$setOnInsert`），不会跑一遍空迁移。没有迁移链的集合完全不写 `_schema_version`，文档里不留多余字段。

## 编写迁移的注意事项

- **只能追加**。改动已经发布过的步骤，线上那部分已经迁移过的文档不会重跑，两批数据会就此分叉。
- **考虑中途失败**。一条链里的多个步骤不是一个事务：第 2 步抛异常时第 1 步的修改不会落库（整次加载失败，什么都没写），但下次加载会从头重跑 1、2 两步。尽量让每一步幂等。
- **别依赖外部服务**。`migrate` 在行锁内同步执行，阻塞住就意味着这一行加载不动。
- **先在预发环境跑**。迁移失败会让对应的角色/账号无法登录。

## 热更

GM 命令 `reload_orm_schema`（`write` 级）会把 schema 和迁移链一起换掉：先只读地编译新的迁移链，再加载新 schema，两边都准备好之后才一起生效。任意一边失败就整体放弃，进程里的旧 schema 和旧迁移链原封不动。

schema 加了字段而迁移没跟上，之后加载的旧文档会直接撞在类型检查上，所以这两者必须同进同出。

已经加载到内存的文档不会被回溯迁移——热更只影响之后的加载。
