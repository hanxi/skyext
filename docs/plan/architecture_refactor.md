# 架构重构设计

> **状态：方向已确认，分阶段实现中。** 现状以[架构概览](../overview.md)和代码为准，本文只描述目标。
>
> 已确认的决定：引入独立网关层，同时保留 gate 与 role 同进程部署；区服采用"节点池共享、game 作命名空间"；
> 从阶段 1（常驻实体）开始实现。

现在的实体系统解决了"单个玩家的数据放在哪、怎么不丢、怎么不同时在两个地方"。它没有回答的是一个游戏服务器的另外几件事：客户端连接放在哪、区服怎么隔离、全服唯一的东西（排行榜、公会）怎么跑、两个玩家之间的交易怎么保证、消息怎么一次发给很多人。本文给出这五件事的方案和推进顺序。

## 设计原则

沿用 [不做的事](../non-goals.md) 的三条：成本不转嫁给写玩法的人；不在现成设施旁边造一个更差的；不加拦不住任何人的防护。另外两条针对本次重构：

- **能用实体系统表达的就用实体系统。**它已经有单活（etcd 锁 + fence）、持久化、路由、故障接管、停服卸载。新能力优先做成实体的一种用法，而不是第二套机制。
- **连接和状态分开。**玩家的 TCP 连接是最脆弱、重建代价最大的东西（客户端要重连、重新登录、重新拉数据），状态迁移不应该连带断开连接。

## 一、独立网关层

### 现状的问题

客户端连接、gate、实体必须在同一个 role 节点上（登录时 `NOT_THIS_NODE` 重定向）。后果：

- **逻辑节点不能无感重启。**发版、热更不了的改动、节点迁移机器，都要踢掉这个节点上的全部玩家。
- 粘性路由避免了扩容踢人，但实体迟早要回到 HRW 指定的节点，回去的方式只有"玩家下线后再上线"。
- 客户端要知道每个逻辑节点的网关地址（robot 的 `gate_nodes` 配置）。

### 方案

新增 **gate 节点**，只管连接，不持有玩法状态：

```
客户端 ──TCP/WS──> gate 节点 ──cluster──> role 节点（实体）
                     │  会话表：session -> { rid, owner_node }
                     └─ 下行推送：实体 cluster.send(gate_node, "push", session, bytes)
```

- **登录**在 gate 节点完成：校验 JWT、校验 rid 归属，再调用实体的 `bind_session(rid, gate_node, session_id)`。实体加载在哪个节点由实体系统决定，gate 只记下返回的 `owner_node`。
- **上行**：gate 把客户端包按会话**直接发给 owner_node**（会话亲和），不走每条消息的路由计算，也不经过粘性转发那一跳——这样同一个玩家的消息天然保序。
- **下行**：实体持有 `{gate_node, session_id}`，推送直接 `cluster.send` 回 gate。
- **断线**：gate 通知实体 `unbind_session`，实体进入现有的闲置卸载计时。

### 无感迁移（这次重构的核心收益）

实体要离开当前节点时（停服、交接），不再踢客户端，而是通知 gate "这个会话换地方了"：

1. 实体卸载前向 gate 发 `migrate(session_id)`；gate 暂停该会话的上行，把收到的包缓存起来。
2. 实体落库、释放锁。
3. gate 重新调用 `bind_session`，实体在新节点加载（HRW 指向的节点）。
4. gate 把缓存的包按顺序发往新 owner，恢复转发。

玩家看到的是一次几十到几百毫秒的卡顿，而不是掉线重登。逻辑节点从此可以滚动发版。

### 要决定的点

| 问题 | 选项 | 建议 |
|------|------|------|
| gate 是否解析协议 | A. 只看包头，原样转发字节，实体侧解码 B. gate 完整解码 sproto | **A**。gate 不依赖协议定义，协议热更不用动 gate；限流、鉴权在会话层做就够了 |
| 同时支持多种实体接入 | 会话绑定一个主实体（role），其他实体经 role 转发 | 先只支持一个主实体，够用再扩 |
| WebSocket | gate 节点内置，还是继续用 goscon 在前面转 TCP | 继续用 goscon，gate 只做 TCP |
| 现有同进程模式 | 保留为"gate 与 role 同节点部署"的特例 | 保留：小规模部署一个进程起两个角色即可，代码路径相同 |

**代价**：每条客户端消息多一次节点间跳转（同机房约 0.1–0.5ms），gate 节点挂掉会断开它上面的连接（但不丢任何玩家数据）。

## 二、区服隔离

### 现状

schema 里有 `server`（客户端看到的区服）和 `game`（玩法范围，合服就是把多个 server 映射到同一个 game），但实体放置完全不看它们——所有区服的角色在一个节点池里。框架没有表态。

### 方案：节点池共享，玩法范围是命名空间

- **逻辑节点不按区服划分。**任何 role 节点都能承载任何区服的角色。资源利用率高，开新服不用加节点，合服只改 `server2game` 映射和角色文档的 `game` 字段，不用搬进程。实体 ID 是全局唯一的 snowflake，合服不会撞 ID。
- **玩法范围体现在"按 game 分片的全局实体"上**：排行榜、公会列表、世界 Boss 都以 `game` 为维度各起一个（见下一节），玩家只和自己 game 的那一份交互。
- 文档明确写出这个立场。需要物理隔离的场景（比如某个区服要独占机器）不在框架内支持，靠部署层面单独起一套集群。

备选方案是每个 game 一个节点池（服务发现按 `entity:role@game1` 注册）。它的问题是合服要整体搬迁实体、节点数随区服数线性增长，与"成本不转嫁"冲突，不建议。

## 三、全局单例：常驻实体

### 需求

排行榜、公会管理器、世界 Boss、聊天频道：每个 game 只能有一份，挂了要能在别的节点接管，停服要落库。

### 方案：做成实体，不另造选主机制

单例天然满足实体系统的全部假设——按 ID 寻址、单活、需要持久化、需要故障接管。缺的只有三点：

1. **常驻**：实体类型配置 `resident = true`，不进闲置卸载计时。
2. **主动激活**：普通实体靠第一条消息激活，单例要在没人找它时也跑着（比如每分钟结算一次排行）。新增 `preload` 配置（静态 ID 列表，或者按 `server2game` 里的 game 生成），每个节点启动后、以及集群成员变化后，加载 HRW 落在自己身上的那几个 ID。
3. **定时器**：实体内的定时器回调必须走实体的串行队列并检查租约（失租后不能再跑）。提供 `entity:timer(name, sec, fn)`，卸载时自动取消。

ID 约定：单例实体的 ID 由 `(类型, game)` 确定性地算出（比如 game 名的哈希），任何节点都能直接 `router.call("rank", rank_id(game), ...)`。

**数据量提醒**：排行榜这类数据不适合整份放进一个 Mongo 文档（16MB 上限、每次存盘都要 diff 整份）。单例实体的 handler 可以自己管理一个独立集合，按需读写；实体系统只保证"同一时刻只有它在写"。

## 四、跨实体事务

### 原则

实体加载期间，内存是权威，数据库只是快照，所以不能靠 Mongo 多文档事务来保证跨实体一致。跨实体的操作一律通过**可靠消息 + 幂等**来做。

### 两种模式

- **单向转移（赠送、发奖励、邮件附件）**：发起方先在自己身上扣，再 `reliable_send` 给接收方加。可靠消息保证至少一次投递，接收方用 `msg_id` 去重。现在已经能这样写，补一个示例和文档即可。
- **双向交换（交易）**：引入一个**交易实体**（`auto_create = true`，ID 为新分配的 snowflake）作为协调者，持久化自己的状态机：
  1. 交易实体向双方 `reliable_send("reserve", items)`；双方把物品挪到"冻结区"，并回执给交易实体。
  2. 双方都冻结成功 → 向双方发 `commit`（冻结区物品转给对方）；任一方失败或超时 → 向双方发 `release`（解冻）。
  3. 每一步都是可靠消息、都以 `msg_id` 幂等；交易实体重启后从持久化的状态继续推进。

  框架提供 `skyext.entity.saga` 帮助库（状态机持久化、超时、回执收集），示例实现一个双人交易。

## 五、广播与组播

### 方案：频道挂在 gate 层

广播的对象是"在线连接"，而连接在 gate 上，所以频道也放在 gate 层：

- 每个 gate 节点维护 `频道 -> 本地会话集合`。
- 订阅/退订由实体发起（玩家加入公会时，role 实体通知自己会话所在的 gate），gate 断线时自动退订。
- 发布：`channel.publish(name, msg)` 发给所有 gate 节点（服务发现里的 `gate` 服务），每个 gate 只投递给本地订阅者。全服广播就是一个所有会话都订阅的频道，按 game 广播是 `game:<id>` 频道。

在独立网关层落地之前，可以先实现一个退化版本：发给所有 role 节点，由各 agent 推给本地绑定的实体。接口不变，网关层上线后只换实现。

## 推进顺序

| 阶段 | 内容 | 依赖 |
|------|------|------|
| 1 | 区服立场写进文档；常驻实体（resident、preload、实体定时器）；排行榜示例 —— **已完成** | 无 |
| 2 | 独立网关层：会话、亲和转发、下行推送、登录迁到 gate；同进程部署作为特例保留 | 无 |
| 3 | 无感迁移：卸载/交接时 migrate 会话；滚动发版验证 | 阶段 2 |
| 4 | 频道广播（先退化版，阶段 2 之后换成 gate 版） | 退化版无依赖 |
| 5 | saga 帮助库与交易示例；单向转移示例 | 无 |

阶段 1、4（退化版）、5 互相独立，可以和阶段 2 并行。

## 不在本次范围

- **场景与 AOI**：实时同步类玩法（MMO 地图、ARPG 战斗）需要按空间分片的场景服，与"按 ID 寻址的实体"是不同的模型。本框架定位于以玩家数据为中心的游戏（SLG、卡牌、休闲、放置），场景服另行设计。
- **etcd 不可用时的降级**：目前 etcd 连续约 28 秒不可达会全服掉线，见[架构概览](../overview.md)。缓解方案（比如租约未知期间只读服务）需要单独评估一致性代价。
